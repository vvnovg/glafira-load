# Сьюты

Сьют — сценарий нагрузочного теста: последовательности шагов, которые вызывают операции реестра с данными,
проверками и извлечёнными значениями, которые вы описываете. Сьюты лежат в `suites/<имя>/suite.yaml` и правятся
руками в текстовом редакторе; Glafira их показывает, проверяет, считает покрытие профиля нагрузки и создаёт заготовку
из реестра. Сьюты видны в левой панели в разделе [[ui:sidebar.suites]], по узлу на папку.

## Файл suites/имя/suite.yaml {#file}

```yaml
format: 1
name: orders
secrets: [API_TOKEN]                      # должны быть на агентах как GLAFIRA_LOAD_SECRET_API_TOKEN
data:
  users: { path: data/users.csv, mode: slice }   # slice — агенты делят строки; shared — у всех весь файл
  skus:  data/skus.jsonl                         # короткая форма, mode: shared
defaults:
  http: { timeout_ms: 5000, headers: { Accept: application/json } }
  kafka: { acks: all }                           # параметры rdkafka продюсера и потребителя
  arrival: poisson                               # poisson | constant
  max_in_flight: 1000                            # на агента
scenarios:
  - id: order-flow
    drives: "http:orders:POST /v1/orders"        # по умолчанию операция первого шага
    on_fail: stop                                # stop | continue
    steps:
      - id: create
        http:
          operation: "http:orders:POST /v1/orders"
          headers: { Authorization: "Bearer {{secret API_TOKEN}}" }
          body: { customerId: "{{users.id}}", items: [{ sku: "{{pick skus.sku}}", qty: "{{int 1 5}}" }] }
        expect: { status: 201, jsonpath: { "$.id": exists } }
        extract: { order_id: "$.id" }
      - id: get
        http: { operation: "http:orders:GET /v1/orders/{id}", path: { id: "{{steps.create.order_id}}" } }
        expect: { status: 200, schema: response, max_ms: 800 }
      - kafka_consume:
          operation: "kafka_consume:orders.created"
          match: { key: "{{steps.create.order_id}}" }
          timeout_ms: 10000
      - kafka_produce:
          operation: "kafka_produce:orders.paid"
          key: "{{steps.create.order_id}}"
          value: { orderId: "{{steps.create.order_id}}", paidAt: "{{now iso}}" }
          encoding: json                              # json | avro
```

Сьют определяется своей папкой; `name` — `[a-z0-9-]`, до 64 символов, и должен совпадать с именем папки (Glafira так
и пишет). Каждый шаг привязан к операции реестра по её ID: метод и путь HTTP-операции и топик Kafka-операции берутся
из реестра, базовый URL и bootstrap Kafka — из стенда ([Агенты и стенды](agents.md#stand)). Неизвестное поле в любом
месте файла — ошибка, а не молчаливый пропуск: опечатка в имени поля меняла бы нагрузку.

Файлы данных — CSV с заголовком или JSON Lines, `path` относительно папки проекта и внутри неё. Каждая итерация
сценария берёт следующую строку каждого набора по кругу. При `mode: slice` контроллер делит строки между агентами по
их весам, при `shared` каждый агент получает весь файл.

Значения по умолчанию: `timeout_ms` 5000, `arrival` `poisson`, `max_in_flight` 1000, `mode` `shared`, `on_fail`
`stop`, `kafka_consume.timeout_ms` 10000, `encoding` `json`, `drives` — операция первого шага. Шаг без `id` называется
`step<N>` по позиции, начиная с 1. ID сценариев и шагов, имена наборов данных и секретов — `[A-Za-z0-9_-]`, до 64
символов.

## Шаги {#steps}

| Шаг | Поля |
|---|---|
| `http` | `operation`, `path` (параметры пути), `query`, `headers`, `body` (YAML, уходит как JSON) или `body_text` (как есть), `timeout_ms` |
| `kafka_produce` | `operation`, `key`, `value` (YAML → JSON) или `value_text`, `headers`, `encoding`: `json` или `avro` (схема из контракта, на который указывает операция, id схемы — из Schema Registry стенда) |
| `kafka_consume` | `operation`, `match`: `key` и/или `jsonpath` (карта JSONPath → ожидаемое значение), `timeout_ms` |

Сценарий ведёт одну операцию (`drives`, это должна быть операция одного из его шагов): его частота равна цели этой
операции из профиля, делённой на число шагов с этой операцией в сценарии. Остальные операции сценария получают
нагрузку как следствие. Два сценария с одной ведущей операцией в одном сьюте — ошибка. `on_fail: continue` позволяет
итерации выполнить оставшиеся шаги после непройденной проверки; по умолчанию итерация прерывается.

## Выражения {#expressions}

`{{…}}` внутри любой строки сьюта. Без операторов и вложенности. Строка, целиком состоящая из одного выражения,
сохраняет тип значения: число остаётся числом в JSON-теле.

| Выражение | Значение |
|---|---|
| `users.id` | колонка текущей строки набора `users` |
| `steps.create.order_id` | значение, извлечённое предыдущим шагом итерации |
| `uuid` | UUID v4 |
| `int a b`, `float a b` | случайное число в `[a, b]` |
| `now iso`, `now unix` | время агента: RFC 3339 в UTC или секунды |
| `str n` | случайная строка из `n` латинских букв и цифр |
| `pick skus.sku` | колонка случайной строки набора |
| `secret API_TOKEN` | переменная `GLAFIRA_LOAD_SECRET_API_TOKEN` агента |
| `env.http`, `env.kafka`, `env.schema_registry` | адреса стенда из манифеста |
| `run.id`, `agent.id` | идентификаторы прогона и агента |

Неизвестная форма, набор, колонка или шаг — ошибка проверки с файлом и строкой. Имена `steps`, `env`, `run` и `agent`
для наборов данных заняты.

## Проверки и извлечение {#expect}

| Ключ `expect` | Смысл |
|---|---|
| `status` | число, список чисел или класс: `2xx`, `4xx` |
| `jsonpath` | JSONPath → матчер: `exists`, `{ equals: … }`, `{ matches: "regex" }`, `{ gt: n }`, `{ lt: n }` |
| `schema: response` | ответ соответствует сжатой схеме ответа из реестра: типы полей и обязательность, вложенность до 6 уровней |
| `max_ms` | задержка шага не больше предела |

Непройденная проверка — ошибка шага с кодом `EXPECT_STATUS`, `EXPECT_JSONPATH`, `EXPECT_SCHEMA` или `EXPECT_MAX_MS`.
Для `kafka_consume` те же проверки применяются к значению совпавшего сообщения. `extract` — карта имя → JSONPath по
телу ответа или сообщения; отсутствие пути — `EXTRACT_MISSING`. Следующие шаги читают значения как
`{{steps.<id шага>.<имя>}}`.

## Проверка {#check}

[[ui:suite.check]] на вкладке сьюта или `glafira-load check` в терминале работает без сети и показывает проблемы
уровней [[ui:suite.level.error]] и [[ui:suite.level.warning]] с файлом и строкой. Нажатие на файл и строку проблемы
или [[ui:suite.openFile]] в панели инструментов открывает файл в редакторе, назначенном для него в системе. Вкладка
перечитывает файл по [[ui:suite.check]] и при возврате фокуса в окно, поэтому правки из редактора видны без повторного
открытия вкладки.

Проверяются схема YAML (неизвестные поля, типы), существование операций в реестре (удалённая операция —
предупреждение, отсутствующая — ошибка), разбор всех выражений, файлы данных и колонки, на которые они ссылаются,
секреты (каждый `secret X` перечислен в `secrets`), уникальность ID сценариев и шагов, ссылки `steps.<id>` только на
предыдущие шаги, одна ведущая на операцию, а для `encoding: avro` — наличие у стенда адреса
[[ui:project.env.schema_registry]] (проверяется при старте прогона: вкладка стенда не знает). Объявленные, но не
используемые наборы данных и секреты — предупреждения. Окно прогона выполняет проверку перед стартом и с ошибками не
стартует.

## Покрытие профиля {#coverage}

Таблица покрытия внизу вкладки сравнивает профиль нагрузки со сьютом: для каждой операции —
[[ui:suite.column.target]], [[ui:suite.column.planned]] от всех сценариев (частота сценария × число его шагов с
операцией) и [[ui:suite.column.delta]]; разница больше 10 % цели выделена. Активные операции с цифрами, но без шага
перечислены в строке «Не покрыто». Покрытие считается по сохранённым файлам с профилем `nominal`, а если его нет — с
первым профилем по имени; цели берутся из [Профиля нагрузки](profile.md#targets).

## Создание сьюта из реестра {#create}

Кнопка «+» ([[ui:sidebar.createSuite]]) рядом с [[ui:sidebar.suites]] в левой панели или [[ui:suite.create]] в панели
инструментов вкладки сьюта открывает диалог: введите [[ui:suite.dialog.name]], отметьте [[ui:suite.dialog.operations]]
(активные операции реестра, есть поле поиска) и нажмите [[ui:suite.dialog.create]]. Glafira запишет
`suites/<имя>/suite.yaml` со сценарием на каждую операцию и откроет его. Тело HTTP-шага и значение сообщения Kafka
генерируются по схеме запроса из реестра: `integer` → `{{int 1 100}}`, `number` → `{{float 0 1}}`, `boolean` →
`true`, перечисление → его первое значение, строка → `{{uuid}}` для полей с именами вида `id`, `…_id` или `…Id`,
`{{now iso}}` для полей вида `…_at`, `…At`, `date` или `time`, иначе `{{str 8}}`. Параметры пути получают
`{{str 6}}`, обязательные параметры запроса и заголовки — значение своего типа. `expect.status` — код 2xx операции,
если реестр его знает, иначе класс `2xx`. Шаг `kafka_produce` получает ключ `{{uuid}}`, шаг `kafka_consume` — без
`match`. Операции gRPC и SQL в этой версии в сьют не попадают.

Файл — отправная точка: откройте его в редакторе и замените сгенерированные значения наборами данных и извлечёнными
значениями.

## Проверка в терминале {#cli}

```bash
glafira-load check <проект> [--suite <имя>]
```

Без `--suite` проверяются все сьюты проекта. Код возврата 0, если ошибок нет (предупреждения печатаются, но не ломают
проверку), 4 — если ошибки есть, 3 — если проект не читается или в нём нет сьютов. Запускайте её в CI рядом с тестами
сервисов; установка CLI описана в разделе [Установка агента](agents.md#install).
