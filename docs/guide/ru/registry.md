# Реестр операций

Реестр операций — список всех операций тестируемой системы со схемами запроса и ответа. Он строится по контрактам
сервисов и хранится в `registry/operations.yaml`. Откройте его пунктом [[ui:sidebar.registry]] в левой панели.

## Что такое операция {#operations}

Операция — то, что нагрузка будет вызывать или отправлять. Видов пять, и вид определяет её ID:

| Вид | ID | Откуда берётся |
|---|---|---|
| HTTP | `http:<сервис>:<МЕТОД> <путь>`, путь как в контракте, с `{param}` | OpenAPI 3.0/3.1, Swagger 2.0, контроллеры Spring |
| Kafka: отправка | `kafka_produce:<топик>` | AsyncAPI `publish`/`send`, `kafkaTemplate.send("topic", …)` в Spring, файлы схем |
| Kafka: чтение | `kafka_consume:<топик>` | AsyncAPI `subscribe`/`receive`, `@KafkaListener(topics = …)` в Spring |
| gRPC | `grpc:<сервис>:<package.Service/Method>` | `rpc` в файлах `.proto`; стриминг помечается `client`, `server` или `bidi` |
| SQL | `sql:<сервис>:<имя>` | добавляется вручную, имя задаёте вы |

В ID операций Kafka нет сервиса: топик общий для всех, кто в него пишет или из него читает. По ID операцию находят
шаблон нагрузки ПРОМ и профиль нагрузки, поэтому он не меняется, пока не меняется контракт.

Таблицу можно фильтровать по сервису, виду, источнику и статусу и искать по ID или имени. Выберите строку, чтобы
увидеть адрес, файл и строку источника ([[ui:service.openFile]] открывает его), версии, в которых операция появилась
и встречалась последний раз, и схемы.

## Схемы {#schemas}

Схемы запроса и ответа показываются сжатым деревом: имя поля, тип, значения перечисления и пример, если он есть в
контракте. Звёздочка `*` отмечает обязательное поле. Дерево ограничено 6 уровнями и 200 полями на уровне; всё, что
дальше, обрезается с пометкой [[ui:registry.truncated]]. Тип, который ссылается сам на себя, обрывается на повторе и
показывается как `ref:<Тип>`. Ненайденная ссылка `$ref` получает тип `unresolved`, а в отчёте разбора появляется
предупреждение.

Для HTTP ответ — первый ответ 2xx; остальные коды перечислены по номерам. По отпечатку схем (без примеров и описаний)
реестр понимает, изменилась ли операция.

## Повторный разбор {#rescan}

Каждый [[ui:service.scan]] сливает новый результат с реестром:

- операция с новым ID — **новая**;
- операция, у которой изменились схемы или адрес, — **изменённая**; её схемы и источник заменяются;
- операция сервиса, которой больше нет в контрактах, — **удалённая**: она остаётся в реестре со статусом
  [[ui:registry.status.removed]] и версией, в которой встречалась последний раз;
- удалённая операция, которая появилась снова, — **вернувшаяся**, она снова [[ui:registry.status.active]].

[[ui:registry.manual]] — теги, владелец и заметки — разбор никогда не трогает. Удалённую операцию можно убрать
окончательно кнопкой [[ui:registry.deleteRemoved]]. Версия, в которой операция встречалась последний раз, обновляется,
когда меняется версия или коммит клона либо сама операция изменилась или вернулась; неизменившаяся операция при
повторном разборе той же версии и коммита её сохраняет. Поэтому повторный разбор без изменений в контрактах оставляет
файл байт в байт прежним. Операции отсортированы по сервису и ID, поэтому `git diff` остаётся читаемым.

## Дифф {#diff}

Каждый разбор пишет снимок в `registry/scans/`. Включите [[ui:registry.diffToggle]], чтобы отметить строки, которые
отличаются между двумя последними снимками: новые, изменённые и удалённые. В разделе разборов под таблицей можно выбрать
любые два снимка — [[ui:registry.diffFrom]] и [[ui:registry.diffTo]]. Включённый дифф переключает фильтр статуса на
любой, чтобы удалённые операции и их отметки были видны. В снимке записано и то, какие поля изменились (добавлены,
удалены, сменили тип или обязательность); [[ui:service.openScan]] в отчёте разбора на вкладке сервиса открывает его. В
версии 0.1.0 изменения по полям есть только в снимках: таблица реестра отмечает строки, но полей не перечисляет.

## Ручные операции {#manual}

У некоторых операций нет контракта: SQL-запросы, адрес внешней системы, топик, который никто не описал. Добавьте их
кнопкой [[ui:registry.addManual]]: выберите сервис и вид, заполните адрес (для SQL — имя операции, например
`find-order-by-id`) и описание. Форма показывает получившийся ID. Ручные операции разбор не меняет и не удаляет;
[[ui:common.delete]] в панели операции убирает её.

Для SQL раздел [[ui:registry.tables]] показывает таблицы и колонки, которые Glafira нашла в миграциях сервисов
(Flyway, Liquibase XML и formatted SQL, golang-migrate). Операций миграции не создают: они помогают назвать запросы,
которые будет выполнять нагрузка.

## Предупреждения импортёров {#warnings}

Glafira читает контракты, ничего не компилируя и не запуская, поэтому кое-что вычислить нельзя. Такие места становятся
предупреждениями с файлом и строкой в отчёте разбора; остальная часть файла всё равно разбирается.

- **Spring.** Путь, заданный константой (`@GetMapping(Paths.SEARCH)`), не вычисляется, и операция пропускается;
  `@RequestMapping` без метода пропускается; топик, заданный не строковым литералом, пропускается. Несколько путей в
  одной аннотации — берётся первый. Тело запроса берётся по имени типа `@RequestBody`, без полей.
- **OpenAPI.** `callbacks` и `links` не читаются; `$ref` на другой файл разрешается только внутри клона, `$ref` на URL
  не разрешается.
- **AsyncAPI.** У сообщения с `oneOf` берётся первый вариант. О серверах с протоколом не Kafka выводится
  предупреждение, а их каналы всё равно читаются как топики Kafka.
- **Файлы схем.** Без сопоставления в разделе [[ui:service.kafkaTopics]] топик угадывается по имени файла. У таких строк
  есть пометка «[[ui:registry.topicGuessed]]»: проверьте топик или добавьте сопоставление на вкладке сервиса.
- **Protobuf.** Ненайденный `import` и неизвестные типы попадают в предупреждения; импорты `google/protobuf/*`
  известны.
- **SQL.** Нераспознанные выражения попадают в предупреждения; changelog Liquibase в YAML и JSON пока не поддерживаются.
