# Agents and stands

Load is generated by agents: copies of the `glafira-load` CLI running on the load machines of a stand. The
application (or `glafira-load run --agents`) is the controller: it sends the suite and a share of the profile to every
agent, receives the metrics as a stream and assembles the result folder on the engineer's machine. Without agents the
load runs in the process of the controller itself: a stand without agents runs inside the application, and
`glafira-load run` without `--agents` in the CLI, which is enough for CI and one machine.

## Installing an agent {#install}

The CLI is one static binary per platform, published next to the installers:
https://github.com/vvnovg/glafira-load-releases/releases. The [[ui:sidebar.about]] screen shows the download command
for the operating system and processor of the current machine; the names are `glafira-load-linux-x86_64`,
`glafira-load-linux-aarch64`, `glafira-load-macos-aarch64`, `glafira-load-macos-x86_64` and
`glafira-load-windows-x86_64.exe`, each with a `.sha256` file next to it. Put the binary into `PATH`, check it with
`glafira-load --version` and start the agent:

```bash
glafira-load agent --listen 0.0.0.0:7420 --token-file ~/.glafira-load/token \
                   --work ~/.glafira-load/agent --keep-runs 10 --drain-ms 5000
```

The agent keeps its state in memory and in `--work` (by default the folder `glafira-load-agent` in the temporary
folder of the system): bundles and files of past runs, of which the newest `--keep-runs` are kept (10 by default).
`--drain-ms` is how long running iterations may finish after a stop (5000 by default). One agent executes one run at
a time; `Ctrl+C` (SIGINT) or SIGTERM stops its current run and then the agent. Running the agent as a system service
(systemd, launchd, Windows service) is described in the
[administrator guide](https://github.com/vvnovg/glafira-load/blob/main/docs/admin.md) (`docs/admin.md` in the repository).

The versions of the application and the agent must match in the major and minor numbers (`0.2`), and the `format` of
the suite must be known to the agent; otherwise the run does not start with the error `AGENT_VERSION`, and the row of
the agent shows both versions.

## Token {#token}

Every request to an agent carries a bearer token. The agent takes it from `--token`, `--token-file` or the environment
variable `GLAFIRA_LOAD_AGENT_TOKEN`, in this order, and does not start without one. Generate a long random string, for
example `openssl rand -hex 32`, and give it to the agent and to the application.

The application keeps tokens in the keychain of the operating system (Keychain, Credential Manager, Secret Service),
never in the manifest. The token is entered in the token field of the agent row on the project tab and saved with
[[ui:agents.saveToken]]; [[ui:agents.removeToken]] deletes it. A token can be set only for an agent of the saved
manifest: save a new agent row first, and save the token before saving the manifest again, because saving the manifest
clears a token that was typed but not saved. Tokens are stored per project folder, stand and agent; when the project
folder is moved or renamed, enter the tokens again.

`glafira-load run --agents` reads the tokens from `GLAFIRA_LOAD_AGENT_TOKEN_<ID>`, where `ID` is the agent ID in upper
case with `-` replaced by `_` (`gen-1` → `GLAFIRA_LOAD_AGENT_TOKEN_GEN_1`). An agent without a token is marked
[[ui:agents.state.no_token]] and the run does not start with `TOKEN_MISSING`; a wrong token is a 401 from the agent,
shown in its row.

## Stand secrets {#secrets}

Suites refer to secrets as `{{secret NAME}}` and list them in `secrets`. The values live only in the environment of the
agents: `GLAFIRA_LOAD_SECRET_<NAME>`. The application does not store or transmit them; the controller only sends the
list of names, and an agent without one of them refuses the run with `SECRET_MISSING` and the names, shown in a banner.
In the samples of errors the values of the secrets are replaced with `***`.

A smoke and a run on a stand without agents execute inside the application or the CLI, so there the variables must be
set in its own environment: set them in the shell before `glafira-load run` or `glafira-load smoke`, and start the
application from a terminal in which they are set.

## A stand with agents {#stand}

Agents belong to a stand of the manifest ([Project and services](project.md#environments)). On the project tab the
stand gets the [[ui:project.env.schema_registry]] address (needed for `encoding: avro`) and the [[ui:agents.title]]
table: [[ui:agents.id]], [[ui:agents.url]], [[ui:agents.weight]] and the token. [[ui:agents.add]] adds a row.
In the file:

```yaml
environments:
  - id: test
    kind: test
    http: https://orders.test.local
    kafka: kafka-1.test.local:9092
    schema_registry: https://sr.test.local
    agents:
      - { id: gen-1, url: http://10.0.1.11:7420 }
      - { id: gen-2, url: http://10.0.1.12:7420, weight: 2 }
```

The agent ID is unique in the stand. The URL is `http://` inside the network of the stand; `https://` is accepted when
the agent is behind a reverse proxy with a certificate trusted by the system. The agent itself has no TLS in this
version. A stand without agents is allowed: a run on it executes inside the application.

## Weights {#weights}

The controller divides the targets of the profile by the weights: an agent with weight 2 next to an agent with weight
1 gets two thirds of every target and two thirds of the rows of every `slice` data set. The weight is 1 by default and
at least 1. Use it when the load machines differ in size, or to run two agents on one machine for a test.

## Checking the agents {#probe}

[[ui:agents.probe]] on the project tab (for the agents of the saved manifest) and the agent rows of the run window ask
every agent for its version, operating system, processor and number of cores and whether it is busy. The states:
[[ui:agents.state.ready]], [[ui:agents.state.busy]] (with the ID of the run it is executing),
[[ui:agents.state.unreachable]] (no answer, the reason is in the row), [[ui:agents.state.version]] (both versions in
the row) and [[ui:agents.state.no_token]]. When a run starts, the controller asks every agent again: the run does not
start if an agent is unreachable, busy, of another version or without a token.

## When an agent is lost {#loss}

An agent streams its metrics once a second; the controller keeps the position of the stream and reconnects after a
break for up to 30 seconds, continuing from the last event (the agent buffers two minutes). If the agent does not come
back, its row turns to [[ui:run.agentState.lost]], the run continues on the other agents and the status of the result
is [[ui:run.runStatus.incomplete]]. When the run ends, the controller asks the lost agent to stop and requests its files
once more; if the agent is back by then, they are collected.

Closing the application during a run asks what to do: [[ui:run.close.stop]] stops the run, waits until the folder is
written and closes; [[ui:run.close.leave]] closes at once, and the agents finish the timeline on their own and keep the
files. When the run executes inside the application (a smoke or a stand without agents), the second button is
[[ui:run.close.leaveInside]]. The window close button and `Cmd+Q` on macOS show this question; quitting from the Dock or
logging out of macOS cannot show it, and then the runs are stopped within 3 seconds.

On the next opening of the project the run is listed in [[ui:run.past.title]] as [[ui:run.past.inProgress]]; the list
asks the agents for their files and completes the folder, with the status [[ui:run.runStatus.incomplete]] when some
agent could not be reached or its files were already deleted by `--keep-runs`. A run that an agent is still executing
stays unfinished until the agent is done.
