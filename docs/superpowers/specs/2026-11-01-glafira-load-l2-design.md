# Glafira for Load Testing — этап L2 «Сьют, агенты и прогон»

**Дата:** 2026-11-01
**Статус:** согласована в обсуждении, на ревью текста
**Концепция:** `2026-10-31-glafira-load-concept-design.md`
**Предыдущий этап:** `2026-10-31-glafira-load-l1-design.md` (реализован в 0.1.0)

---

## 1. Объём

В L2 входит:

1. Формат сьюта `suites/<имя>/suite.yaml`: сценарии, шаги HTTP и Kafka, проверки, извлечение, данные,
   выражения; разбор, проверка и покрытие профиля в `glafira-load-model` (§3).
2. Агент `glafira-load agent` на машинах нагрузки и HTTP-протокол между контроллером и агентами (§4).
3. Движок генерации нагрузки: открытый цикл по RPS, клиенты HTTP и Kafka, проверки, метрики (§5).
4. Контроллер, общий для приложения и CLI: раздача долей и данных по агентам, сводный поток, файлы прогона (§4, §6).
5. CLI `glafira-load` с командами `run`, `smoke`, `check`, `agent` (§5.4).
6. Экраны «Сьюты» и «Прогон», агенты в форме стенда, IPC и ошибки (§7).
7. Тесты, CI со сборкой CLI, документация (§8–§10).

Не входит: шаги gRPC и SQL (L2b), HTML-отчёт, история прогонов, сравнение и SLA (L3), моки (L4), MCP (L5),
TLS между контроллером и агентом (агент работает в сети стенда), Rhai-скрипты, запись трафика.

### 1.1 Отступления от концепции

Концепция обещала, что раннер пишет результаты в папку, а приложение их импортирует, и что оркестрации из
приложения нет. В обсуждении L2 решено иначе, по образцу распределённого режима JMeter: приложение выступает
контроллером, на машинах нагрузки работают агенты `glafira-load agent`, контроллер раздаёт им сьют и долю
профиля, получает метрики потоком и сам собирает `runs/<дата>/` на машине инженера. Локальный
`glafira-load run` без агентов остаётся для CI и одной машины. Многохостовый запуск «одинаковыми командами с
`--share 1/3`» из концепции заменён агентами. HTML-отчёт раннера перенесён в L3, чтобы графики в отчёте и в
приложении были одними и теми же.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Протоколы шагов | HTTP и Kafka (produce, consume с лагом потребителя). gRPC и SQL — L2b |
| Кто пишет сьют | Руки в текстовом редакторе; приложение показывает, проверяет и создаёт заготовку из реестра |
| Протокол контроллер ↔ агент | HTTP/1.1 + JSON, поток метрик через server-sent events, bearer-токен |
| Кто к кому подключается | Приложение к агентам; адреса агентов в манифесте у стенда, токены в хранилище ОС |
| Модель нагрузки | Открытый цикл по RPS из профиля с потолком одновременности; не виртуальные пользователи |
| Где контроллер | Крейт `glafira-load-engine`, модуль `controller`; один код для приложения и `glafira-load run --agents` |
| Секреты стендов | Переменные окружения агента `GLAFIRA_LOAD_SECRET_<ИМЯ>`; приложение их не хранит и не передаёт |
| Результаты | Файлы в `runs/<дата>/` на машине инженера: посекундные метрики, ошибки с примерами, сводка |
| Окно прогона | Живой ход (графики RPS и p95, счётчики, агенты) и итог; история — только список папок |

## 3. Сьют

### 3.1 Файл `suites/<имя>/suite.yaml`

```yaml
format: 1
name: orders
secrets: [API_TOKEN]                      # должны быть на агентах как GLAFIRA_LOAD_SECRET_API_TOKEN
data:
  users: { path: data/users.csv, mode: slice }   # slice — агенты делят строки; shared — у всех весь файл
  skus:  data/skus.jsonl                         # короткая форма, mode: shared
defaults:
  http: { timeout_ms: 5000, headers: { Accept: application/json } }
  kafka: { acks: all }                           # параметры rdkafka продюсера и потребителя
  arrival: poisson                               # poisson | constant
  max_in_flight: 1000                            # на агента
scenarios:
  - id: order-flow
    drives: "http:orders:POST /v1/orders"        # по умолчанию операция первого шага
    on_fail: stop                                # stop | continue
    steps:
      - id: create
        http:
          operation: "http:orders:POST /v1/orders"   # метод и путь из реестра, базовый URL из стенда
          headers: { Authorization: "Bearer {{secret API_TOKEN}}" }
          body: { customerId: "{{users.id}}", items: [{ sku: "{{pick skus.sku}}", qty: "{{int 1 5}}" }] }
        expect: { status: 201, jsonpath: { "$.id": exists } }
        extract: { order_id: "$.id" }
      - id: get
        http: { operation: "http:orders:GET /v1/orders/{id}", path: { id: "{{steps.create.order_id}}" } }
        expect: { status: 200, schema: response, max_ms: 800 }
      - kafka_consume:
          operation: "kafka_consume:orders.created"
          match: { key: "{{steps.create.order_id}}" }    # key | jsonpath: { "$.orderId": "…" }
          timeout_ms: 10000
      - kafka_produce:
          operation: "kafka_produce:orders.paid"
          key: "{{steps.create.order_id}}"
          value: { orderId: "{{steps.create.order_id}}", paidAt: "{{now iso}}" }
          encoding: json                              # json | avro (схема из контракта, Schema Registry стенда)
```

Пути `data[].path` — относительно папки проекта, внутри неё (`PATH_OUTSIDE_PROJECT` иначе). Файлы данных:
CSV с заголовком или JSON Lines; каждая итерация сценария берёт следующую строку каждого набора по кругу.
`http.path` подставляет параметры пути операции; `query` и `headers` — карты; `body` — YAML, который
сериализуется в JSON, или строка как есть (`body_text`). Неизвестные поля — ошибка `check`, а не молчаливый
пропуск: в сьюте опечатка в имени поля меняет нагрузку.

### 3.2 Привязка к операциям и покрытие

Каждый шаг привязан к операции реестра по ID. Сценарий ведёт одну операцию (`drives`): его частота равна цели
этой операции из профиля, делённой на число её шагов в сценарии. Остальные операции сценария получают нагрузку
как следствие. Покрытие профиля (`model::suite::coverage`) считает по каждой операции цель и расчётную нагрузку
от всех сценариев сьюта (Σ частота сценария × число шагов с операцией) и разницу; операции `active` с цифрами,
но без шагов, — «не покрыто». Две ведущие на одну операцию в разных сценариях одного сьюта — ошибка `check`.

### 3.3 Выражения

`{{…}}` внутри любой строки сьюта. Без операторов и вложенности. Формы:

| Выражение | Значение |
|---|---|
| `users.id` | Колонка текущей строки набора `users` |
| `steps.create.order_id` | Значение из `extract` предыдущего шага итерации |
| `uuid` | UUID v4 |
| `int a b`, `float a b` | Случайное число в `[a, b]` |
| `now iso`, `now unix` | Время агента: RFC 3339 в UTC или секунды |
| `str n` | Случайная строка из `n` латинских букв и цифр |
| `pick skus.sku` | Колонка случайной строки набора |
| `secret API_TOKEN` | Переменная `GLAFIRA_LOAD_SECRET_API_TOKEN` агента |
| `env.http`, `env.kafka`, `env.schema_registry` | Адреса стенда из манифеста |
| `run.id`, `agent.id` | Идентификаторы прогона и агента |

Неизвестная форма, набор, колонка или шаг — ошибка `check` с файлом и строкой. Строка, целиком состоящая из
одного выражения, сохраняет тип значения (число остаётся числом в JSON-теле).

### 3.4 Проверки `expect`

| Ключ | Значение |
|---|---|
| `status` | Число, список чисел или класс `2xx`, `4xx` |
| `jsonpath` | Карта JSONPath → матчер: `exists`, `{ equals: … }`, `{ matches: "regex" }`, `{ gt: n }`, `{ lt: n }` |
| `schema: response` | Ответ соответствует сжатой схеме реестра: типы полей и обязательность, вложенность до 6 уровней |
| `max_ms` | Задержка шага не больше |

Непройденная проверка — ошибка шага с кодом `EXPECT_*`; итерация прерывается, если у сценария не задано
`on_fail: continue`. Для `kafka_consume` проверки те же, применяются к значению сообщения. `extract` — карта
имя → JSONPath по телу ответа или сообщения; отсутствие пути — ошибка `EXTRACT_MISSING`.

### 3.5 Команда `check`

Без сети. Проверяет: схему YAML (неизвестные поля, типы), существование операций в реестре (`removed` —
предупреждение, нет вовсе — ошибка), разбор всех выражений, файлы данных и ссылки на их колонки, объявленные
секреты (каждый `secret X` объявлен в `secrets`), уникальность `id` сценариев и шагов, ссылки `steps.<id>`
только на предыдущие шаги, одна ведущая на операцию. Отчёт — список `{ level, file, line, message }`.
Схема сьюта, выражения, `check` и покрытие — в `glafira-load-model/src/suite/`, без I/O: приложение и агент
читают сьют одним кодом.

## 4. Агент и протокол

### 4.1 Запуск агента

```
glafira-load agent --listen 0.0.0.0:7420 --token-file ~/.glafira-load/token \
                   --work ~/.glafira-load/agent --keep-runs 10 --drain-ms 5000
```

Токен — из `--token-file`, `--token` или переменной `GLAFIRA_LOAD_AGENT_TOKEN`; без токена агент не стартует.
Состояние только в памяти и в `--work`: бандлы и файлы прогонов, старше `--keep-runs` удаляются. Секреты стенда —
переменные окружения агента `GLAFIRA_LOAD_SECRET_<ИМЯ>`. Один агент исполняет один прогон за раз.

### 4.2 Стенд в манифесте

```yaml
environments:
  - id: test
    kind: test
    http: https://orders.test.local
    kafka: kafka-1.test.local:9092
    schema_registry: https://sr.test.local      # для encoding: avro
    agents:
      - { id: gen-1, url: http://10.0.1.11:7420 }
      - { id: gen-2, url: http://10.0.1.12:7420, weight: 2 }   # получит 2/3 нагрузки
```

`agents[].id` уникален в стенде, `weight` ≥ 1, по умолчанию 1. Токены агентов — в хранилище ОС (`keyring`,
сервис `glafira-load`, ключ `<проект>/<стенд>/<агент>`), в манифест не попадают. `url` с `https://` принимается
через `rustls` с системными корнями, если агент стоит за обратным прокси; своего TLS у агента в L2 нет.

### 4.3 HTTP API агента

JSON, заголовок `Authorization: Bearer <токен>`; без него или с чужим — `401`.

| Метод | Назначение |
|---|---|
| `GET /v1/info` | `{ version, os, arch, cpus, busy: run_id? }` |
| `POST /v1/runs` | Бандл (§4.4); ответ `202 { run_id }`, `409 AGENT_BUSY`, `412 SECRET_MISSING { names }`, `422 SUITE_INVALID`, `426 AGENT_VERSION { agent, controller }` |
| `GET /v1/runs/{id}/events` | SSE с `id:` событий: `tick` раз в секунду (метрики по операциям и сценариям за секунду), `phase` при смене фазы, `error` с примером (не чаще одного в секунду на код и операцию), `done` со сводкой агента. `Last-Event-ID` — продолжение с нужного места из буфера последних 120 с |
| `POST /v1/runs/{id}/stop` | Мягкая остановка: новые итерации не стартуют, текущие дорабатывают до `--drain-ms` |
| `GET /v1/runs/{id}/files` | `tar` с `metrics.jsonl`, `errors.jsonl`, `summary.yaml`, `hist.bin`, `agent.log` |
| `GET /v1/runs` | Список прогонов в `--work` со статусами, для достраивания незавершённых (§6.3) |

Контроллер и агент сравнивают `format` сьюта и мажор и минор версии бинарника; расхождение — `AGENT_VERSION`.

### 4.4 Бандл прогона

`multipart/form-data`: `run.json` (`run_id`, `agent_id`, `suite_name`, адреса стенда, список нужных секретов,
цели операций уже умноженные на долю агента, таймлайн фаз, `max_in_flight`, `arrival`), `suite.yaml` и файлы
данных (для `mode: slice` — только строки этого агента, нарезанные контроллером по весам; для `shared` — целиком).

### 4.5 Контроллер (`glafira-load-engine::controller`)

Один код для приложения и `glafira-load run --agents`:

1. Читает проект, сьют, профиль и стенд; выполняет `check`; считает цели и покрытие.
2. Опрашивает `GET /v1/info` всех агентов стенда: занятый, недоступный или с другой версией — отказ до старта.
3. Делит цели по весам агентов и строки `slice`-наборов по тем же весам (остаток — первому).
4. Отправляет `POST /v1/runs` всем; если хоть один отказал — `stop` уже запущенным, ошибка.
5. Читает SSE всех агентов, сводит `tick` в общий посекундный ряд по `t`, пишет `runs/<дата>/` (§6).
6. По `done` от всех или по `stop` забирает `GET /v1/runs/{id}/files` в `agents/<id>/`, считает сводку.

Обрыв SSE — переподключение с `Last-Event-ID` до 30 с; дальше агент помечается `lost`, прогон продолжается на
остальных, статус итога `incomplete`. Остановка агента по `stop` при `lost` повторяется при сборе файлов.

### 4.6 Локальный режим

`glafira-load run <проект> --profile peak --env test` без агентов исполняет нагрузку в своём процессе тем же
контроллером с «встроенным агентом» (тот же код движка без HTTP). `smoke` и `check` всегда локальные.

## 5. Движок (`glafira-load-engine`)

### 5.1 Планировщик

Для каждого сценария — задача на `tokio`, выпускающая итерации по расписанию: частота = цель ведущей операции ×
значение таймлайна в текущую секунду (0…300 %) ÷ число шагов ведущей операции в сценарии. Интервалы между
итерациями экспоненциальные (`arrival: poisson`) или ровные (`constant`). Итерация — отдельная задача; стенда
планировщик не ждёт. Потолок одновременных итераций `max_in_flight` на агента (сьют, `--max-in-flight` или
форма прогона): при достижении итерация не стартует и считается `dropped` — видимый сигнал, что стенд не держит
профиль. Таймлайн приходит из `glafira-load-model::profile::timeline`, как в L1.

### 5.2 Клиенты

- HTTP — `reqwest` с `rustls`, HTTP/1.1 и HTTP/2, пул соединений на агента, `keepalive`; редиректы не
  следуются (код 3xx — ответ как есть).
- Kafka — `rdkafka` с теми же feature'ами, что в Glafira for Kafka (`cmake-build`, `ssl-vendored`,
  `libz-static`, `zstd`). Продюсер один на агента, `acks` и прочее — из `defaults.kafka`. `kafka_consume` —
  один потребитель на топик с группой `glafira-load-<run_id>-<agent_id>`, читает с конца с момента старта,
  держит буфер последних сообщений (по умолчанию 10 000 или 60 с) и шаг ждёт в нём совпадение по `match`;
  таймаут — ошибка `TIMEOUT`. Лаг потребителя снимается раз в секунду через смещения.
- Avro — `apache-avro`; схема из файла контракта, на который указывает операция реестра, id схемы — по Schema
  Registry стенда (`GET /subjects/<топик>-value/versions/latest`), кэш на прогон; формат Confluent (магический
  байт, id, тело). Без `schema_registry` в стенде `encoding: avro` — ошибка `check`.

### 5.3 Метрики

Раз в секунду, по операции и по сценарию: число запросов, ошибки по коду, `dropped`, задержки в `hdrhistogram`
(p50, p90, p95, p99, max), байты запроса и ответа, для `kafka_consume` — лаг потребителя. Коды ошибок:
`HTTP_4xx`, `HTTP_5xx`, `TIMEOUT`, `CONNECT`, `EXPECT_STATUS`, `EXPECT_JSONPATH`, `EXPECT_SCHEMA`,
`EXPECT_MAX_MS`, `EXTRACT_MISSING`, `KAFKA_PRODUCE`, `KAFKA_CONSUME`, `AVRO_ENCODE`. Итог прогона — гистограммы,
слитые по всей длительности и всем агентам: гистограммы складываются точно, перцентили не усредняются.
Примеры ошибок: до 5 на код на операцию, с телом запроса и ответа до 4 КБ; значения секретов в заголовках и
телах заменяются на `***`.

### 5.4 Команды CLI и коды возврата

| Команда | Что делает |
|---|---|
| `run <проект> --profile <имя> --env <стенд> [--agents] [--max-in-flight N] [--out runs/<дата>]` | Прогон по профилю, локально или на агентах стенда |
| `smoke <проект> --suite <имя> --env <стенд>` | Каждый сценарий ровно один раз последовательно; список сломанных шагов с причиной и примером |
| `check <проект> [--suite <имя>]` | §3.5, без сети |
| `agent …` | §4.1 |

Коды возврата: 0 — завершено, 2 — остановлено (`stop`, `Ctrl+C`), 3 — ошибка запуска (`SECRET_MISSING`,
агент недоступен, занят, другая версия), 4 — `check` или `smoke` нашли ошибки. `Ctrl+C` в локальном `run` равен
`stop`. Вывод `run` в консоль: строка в секунду с суммарным RPS, p95 и ошибками; по окончании таблица итогов.

## 6. Файлы прогона `runs/<дата-время>/`

### 6.1 Состав

```
runs/2026-11-02T14-30-00/
  run.yaml          сьют, профиль, стенд, агенты с весами и версиями, коммит проекта, версии сервисов из
                    реестра, начало, конец, статус: completed | stopped | incomplete | failed
  metrics.jsonl     сводный посекундный ряд: {"t": 12, "op": "http:orders:POST /v1/orders", "n": 480,
                    "err": {"HTTP_5xx": 3}, "dropped": 0, "p50": 41, "p95": 97, "p99": 180, "max": 412,
                    "bytes_in": 120400, "bytes_out": 51200} и такие же строки с "scenario" вместо "op";
                    для kafka_consume ещё "lag"
  phases.yaml       фазы с фактическим временем начала и целевым процентом
  errors.jsonl      примеры ошибок: код, операция, сценарий, шаг, агент, время, запрос и ответ (обрезанные)
  summary.yaml      итог по операциям и сценариям: запросов, RPS средний и пиковый, ошибки по кодам и доля,
                    p50/p90/p95/p99/max, dropped, цель из профиля и достигнутый процент
  agents/<id>/      сырые файлы агента: metrics.jsonl, errors.jsonl, summary.yaml, hist.bin, agent.log
```

Имя папки — старт в UTC. Все `t` — секунды от старта прогона. `summary.yaml` и `run.yaml` отсортированы и
стабильны; их можно коммитить по желанию. Сводные перцентили считаются из `hist.bin` агентов (формат
`hdrhistogram` interval log), `metrics.jsonl` хранит только числа для графиков. Ориентир объёма: 50 операций и
час прогона — около 30 МБ `metrics.jsonl`.

### 6.2 Смок

`runs/smoke-<дата-время>/` с `run.yaml`, `errors.jsonl` и `smoke.yaml` (сценарий → шаг → `ok` или код и причина).

### 6.3 Незавершённый прогон

Если приложение закрылось во время прогона, агенты дорабатывают до конца таймлайна и хранят файлы. При
следующем открытии проекта `run_list` видит `run.yaml` без `end`, контроллер опрашивает агентов (`GET /v1/runs`,
`/files`) и достраивает папку; статус `incomplete`, если кого-то не дозвался или файлы уже удалены по
`--keep-runs`.

## 7. Экраны и IPC

### 7.1 Дерево и вкладки

Дерево слева получает узлы «Сьюты» (по узлу на `suites/<имя>`) и «Прогон». «Стенды» остаются в форме проекта.

| Вкладка | Содержимое |
|---|---|
| Проект → стенд | К адресам добавляются `schema_registry` и таблица агентов: id, URL, вес, токен (поле с сохранением в хранилище ОС, в манифест не пишется), «Проверить» → версия, ядра, занят ли, или ошибка |
| Сьют | Слева сценарии и шаги деревом (вид шага, операция, проверки); справа карточка выбранного шага как YAML только для чтения; сверху «Открыть файл», «Проверить» (= `check`: ошибки и предупреждения с файлом и строкой, «Открыть файл» на строке); внизу покрытие профиля: операция — цель RPS — расчётная нагрузка — разница, и «не покрыто». Вкладка перечитывает файл при изменении на диске. «Создать сьют» → диалог: имя, операции из реестра галочками → файл с шагом на операцию, тело по схеме запроса с генераторами по типам (`string` → `{{str 8}}`, `integer` → `{{int 1 100}}`, `uuid` по формату, `date-time` → `{{now iso}}`), `expect.status` по первому 2xx |
| Прогон | Форма: сьют, профиль, стенд, режим (`run` / `smoke`), `max_in_flight`; агенты стенда со статусом «готов / занят / недоступен / версия»; «Запустить», «Остановить». Во время прогона: фаза и прогресс таймлайна, два графика на uPlot (суммарный RPS: цель и факт; p95 по выбранным операциям), счётчики запросов, ошибок, `dropped`, таблица операций с живыми колонками. По окончании — `summary.yaml` таблицей с сортировкой и «Открыть папку». Ниже «Прошлые прогоны»: папки `runs/` с датой и статусом; выбор показывает их `summary.yaml` |

Перед запуском окно выполняет `check` и не стартует с ошибками. Уход с вкладки прогон не прерывает; закрытие
приложения во время прогона спрашивает подтверждение и объясняет, что агенты доработают сами (§6.3).

### 7.2 IPC

| Команда | Параметры | Ответ |
|---|---|---|
| `suite_list` / `suite_get` | `project` / `project, name` | `[SuiteMeta]` / `Suite` (разобранное дерево с номерами строк) |
| `suite_check` | `project, name` | `CheckReport { errors, warnings, coverage }` |
| `suite_create` | `project, name, operation_ids` | `SuiteMeta` |
| `agent_set_token` | `project, env_id, agent_id, token` | — |
| `agent_probe` | `project, env_id` | `[AgentStatus]` |
| `run_start` | `project, suite, profile, env, mode, max_in_flight?` | `Channel<RunEvent>` (`tick`, `phase`, `agent`, `error`, `done`) → `RunSummary` |
| `run_stop` | `run_id` | — |
| `run_list` / `run_get` | `project` / `project, dir` | `[RunMeta]` / `RunSummary` |

Типы в `src/api/types.ts` зеркалят Rust-структуры (`serde(rename_all = "camelCase")`), как в L1.

### 7.3 Ошибки

К §11 спеки L1 добавляются:

| code | Причина | Поведение UI |
|---|---|---|
| `SUITE_INVALID` | `check` нашёл ошибки | Отчёт на вкладке сьюта; «Запустить» недоступна |
| `AGENT_UNREACHABLE` | Нет ответа на `/v1/info` | Строка агента красная с причиной |
| `AGENT_BUSY` | Агент исполняет другой прогон | Строка агента с `run_id` |
| `AGENT_VERSION` | Версии не совпадают | Обе версии в строке агента |
| `SECRET_MISSING` | На агенте нет переменной секрета | Имена и агент в баннере |
| `TOKEN_MISSING` | У агента нет токена в хранилище | Подсветка поля токена |
| `RUN_BUSY` | В проекте уже идёт прогон | «Запустить» недоступна, показан идущий |

## 8. Структура репозитория

```
crates/
  glafira-load-model/     + src/suite/{schema, expr, check, coverage}.rs
  glafira-load-engine/    src/{scheduler, http, kafka, avro, expect, extract, metrics, run_files}.rs
                          src/controller/{mod, bundle, agents, merge}.rs  src/agent_api.rs (типы запросов и событий)
  glafira-load-cli/       src/main.rs  src/cmd/{run, smoke, check, agent}.rs   бинарник `glafira-load`
src-tauri/src/
  runs/                   обёртка контроллера: запуск, Channel событий, список и достраивание прогонов
  agents/                 токены в keyring (`storage/secrets.rs` из Glafira for Kafka), probe
src/components/{suites, run}/
dev/fixtures/suites/      orders/suite.yaml, data/users.csv, data/skus.jsonl, сьюты с каждой ошибкой check
```

`glafira-load-engine` и `glafira-load-cli` не зависят от `tauri`. Агент использует `axum`; контроллер —
`reqwest` с `rustls` (уже в зависимостях приложения через updater). Workspace получает оба крейта.

## 9. Тестирование

### 9.1 Автотесты

- `glafira-load-model`: фикстуры на каждый вид шага и каждую ошибку `check` (нет операции, неизвестное поле,
  плохое выражение, нет колонки, ссылка на будущий шаг, необъявленный секрет, две ведущие на операцию); выражения
  таблицей «строка → значение», включая сохранение типа; покрытие — свойство: Σ расчётной нагрузки по операциям
  равна Σ частота сценария × число шагов.
- `glafira-load-engine`: планировщик на `tokio` с `test-util` и `pause()`: за 10 виртуальных секунд при цели
  100 RPS выпущено 1000 ± 5 % итераций; таймлайн `ramp` даёт растущий ряд; `max_in_flight` даёт `dropped`.
  HTTP против `axum`-заглушки: коды, таймаут, `extract` между шагами, редирект как есть, маскировка секретов в
  примерах ошибок. `expect` по каждому матчеру и по схеме. Слияние гистограмм двух агентов равно гистограмме
  всех замеров. Kafka — против Redpanda через `testcontainers`, `#[ignore]` без Docker, в CI на Linux включено:
  produce JSON и Avro, consume с совпадением по ключу и по JSONPath, таймаут, лаг.
- `glafira-load-cli`: `check` и `smoke` на `dev/fixtures/suites/` с кодами возврата; `agent` на свободном
  порту, контроллер в тесте гоняет полный цикл `POST → SSE → files` с HTTP-заглушкой как стендом, включая
  обрыв SSE с продолжением по `Last-Event-ID`, `stop`, `AGENT_BUSY`, `SECRET_MISSING`, `401`.
- `src-tauri`: команды на временном проекте; `run_list` на папках с незавершённым `run.yaml`; токены через
  поддельный `keyring` в тестах, как в семействе.
- Фронтенд (vitest + Testing Library): вкладка сьюта с отчётом `check` и покрытием, диалог создания сьюта,
  вкладка прогона с потоком событий (мок `Channel`), блокировка «Запустить» при ошибках `check` и `RUN_BUSY`,
  форма стенда с агентами; `i18n-check`.

### 9.2 CI

К `ci.yml` добавляется сервис Redpanda в job `linux`. `release.yml` получает job сборки CLI: Linux x86_64 и
arm64 (musl, статически), macOS arm64 и x86_64, Windows x64; артефакты `glafira-load-<os>-<arch>[.exe]`
кладутся в релиз рядом с установщиками. `cargo deny` покрывает новые крейты.

## 11. Критерии готовности

1. `glafira-load check` и `smoke` на фикстурном сьюте против локальной заглушки проходят на трёх ОС.
2. Прогон 5 минут с двумя агентами на одной машине (разные порты) по профилю `peak`: графики живые, `runs/`
   собран, сумма RPS агентов равна цели ± 5 %.
3. `kafka_produce` и `kafka_consume` на Redpanda в CI: сообщение дождалось совпадения по ключу, лаг в метриках.
4. Обрыв одного агента посреди прогона: прогон продолжается, статус `incomplete`, файлы остальных собраны.
5. Ручная приёмка окна: создать сьют из реестра, проверить, запустить, остановить, открыть итог; стенд с
   агентом без токена и с неверным токеном показывает понятные ошибки.
