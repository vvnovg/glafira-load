# Glafira for Load Testing — концепция

**Дата:** 2026-10-31
**Статус:** согласована в обсуждении, на ревью текста
**Тип:** desktop-приложение (Tauri 2 + Rust + React/TypeScript) и CLI-раннер; пятый продукт семейства Glafira
**Образцы:** Glafira for Apache Kafka (`~/projects/glafira-kafka`) — стек, дизайн, политика, MCP-шлюз;
Glafira for PostgreSQL (`~/projects/glafira-postgres`) — разбиение на концепцию и этапы, заимствование модулей

Документ фиксирует общее видение, решения и этапы. Каждый этап (L1–L6) получает свою спецификацию, план и
реализацию. Первый этап — `2026-10-31-glafira-load-l1-design.md`.

---

## 1. Цель и аудитория

Glafira for Load Testing — настольный инструмент инженера нагрузочного тестирования. По контрактам и коду
тестируемой системы (далее СУТ) он собирает реестр операций, выдаёт Excel-шаблон, в который команда ПРОМ вписывает
наблюдаемую нагрузку, считает профиль нагрузки по коэффициентам, строит сьют в git, который запускается CLI-раннером
с любого хоста, поднимает мок-сервисы, собирает отчёты с графиками и помогает держать сьют в соответствии с новыми
версиями стендов. LLM участвует через MCP-шлюз: читает и предлагает, человек принимает диффом.

**Пользователи:** инженеры НТ и разработчики, которые готовят стенд к приёмке нагрузки. Команда сопровождения ПРОМ
видит только Excel-шаблон и не ставит приложение.

**Ключевые сценарии:**
1. Указать клоны сервисов СУТ, получить реестр операций (HTTP, Kafka, gRPC, SQL) со схемами запросов и ответов.
2. Выгрузить шаблон нагрузки, отдать его команде ПРОМ, импортировать заполненный с проверкой и получить профиль
   нагрузки для стенда по коэффициентам.
3. Собрать сьют (сценарии, данные, профиль) в папке проекта, закоммитить, запустить раннером с удалённого
   терминала или из CI, забрать результаты в приложение и получить отчёт с графиками и вердиктом по SLA.
4. Поднять моки внешних зависимостей и соседей по Kafka там, где настоящих сервисов на стенде нет.
5. После новой версии СУТ увидеть, какие операции изменились, какие сценарии затронуты, и принять правки,
   предложенные ассистентом.

**Не-цели:** фоновый мониторинг и хранение метрик за месяцы (это Prometheus и Grafana), функциональное
автотестирование, запись трафика из браузера, облачная оркестрация сотен агентов, замена JMeter/k6 там, где они уже
встроены в чужие пайплайны.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Источник правды | Проект НТ — папка в git: манифест, реестр операций, нагрузка ПРОМ, профиль, сьюты, данные. Приложение читает и пишет эти файлы; собственной базы с состоянием у него нет, кроме настроек и списка открытых проектов |
| Откуда операции | Из контрактов: OpenAPI/Swagger, Protobuf, AsyncAPI и схемы сообщений (Avro, JSON Schema, proto), SQL-миграции. Единственная эвристика по коду в L1 — сканер аннотаций Spring. Остальные языки (Rust, Go, Python, .NET, Node.js) — через контракты, вручную и через LLM (L5) |
| Нагрузка ПРОМ | Логи ПРОМ недоступны. Приложение генерирует Excel-шаблон из реестра с защищённой колонкой ID; команда ПРОМ заполняет цифры; импорт с проверкой и диффом против прошлого импорта |
| Логи | Логи тестового стенда: источник цепочек операций и правдоподобных данных (L5, через MCP), приложение к отчёту о прогоне (L3), примеры запросов и ответов для моков (L4) |
| Формат сьюта | Декларативный YAML с выражениями (`{{uuid}}`, `{{pick users.csv}}`, `{{steps.create.response.id}}`), JSON-схема, валидация и дифф в приложении. Встраиваемые скрипты не планируются; если YAML упрётся, добавляется блок Rhai отдельным этапом |
| Раннер | Отдельный статический бинарник `glafira-load` без GUI (Linux x86_64/arm64, macOS, Windows). Сьют лежит в git, раннер запускают с терминала или из CI, результаты пишутся в папку, которую приложение импортирует. Оркестрации по SSH из приложения нет |
| Моки | Подкоманда раннера `glafira-load mock`: HTTP, gRPC, соседи по Kafka, ответы с состоянием, запись и воспроизведение |
| Отчёты | Автономный HTML с графиками (строит раннер), экран в приложении с историей и сравнением прогонов, SLA-пороги с вердиктом, экспорт CSV и Prometheus, PDF/DOCX по шаблону |
| LLM | MCP-шлюз только для чтения и предложений, как в Glafira for Kafka: отдельный крейт без зависимостей от сети и Kafka, подтверждение клиентов, аудит, политика |
| Сопровождение | Повторный разбор контрактов с диффом реестра, смоук-прогон сьюта в один поток, пометка затронутых сценариев, предложения правок через MCP |
| Продукт | Apache 2.0, без платных уровней; политика администратора, автообновление, руководство в приложении; i18n с первого дня, ru + en на старте, остальные языки — отдельный этап |
| Код | Отдельный репозиторий (`~/projects/last-test`). Общие модули копируются из Glafira for Kafka с теми же именами и публичными функциями, как сделано в Glafira for PostgreSQL, чтобы позже вынести их в общий код механически |

## 3. Архитектура

```
Desktop (Tauri 2)                                  Терминал / CI
┌─ WebView (React 19 + TS) ────────────────┐       ┌─ glafira-load (CLI, один бинарник) ─────┐
│ дерево: проекты → сервисы, реестр,       │       │ run     — прогон сьюта по профилю       │
│ нагрузка ПРОМ, профиль, сьюты,           │       │ smoke   — каждый сценарий в один поток  │
│ прогоны, отчёты, моки                    │       │ mock    — мок-сервисы по описаниям      │
│ api/ — типизированные invoke() и Channel │       │ report  — HTML из результатов прогона   │
└───────────────▲──────────────┬───────────┘       │ check   — валидация сьюта по схеме      │
                │ events       │ invoke            └───────────────▲─────────────────────────┘
┌───────────────┴──────────────▼─ Rust core ─┐                     │
│ commands/  — IPC, валидация, маппинг ошибок │                     │
│ project/   — манифест, папка проекта, пути  │                     │
│ git/       — версия клона через системный git│                    │
│ scan/      — поиск контрактов, вызов импортёров, слияние реестра  │
│ load/      — шаблон ПРОМ, импорт, профиль   │                     │
│ runs/      — импорт результатов, история (L3)│                    │
│ storage/ policy/ settings/ i18n/ logging/    │                    │
│ mcp/       — реализация Backend шлюза (L5)   │                    │
└──────────────────────────────────────────────┘                    │
crates/                                         общие крейты        │
  glafira-load-model      модель файлов проекта, реестр операций, дифф, расчёт профиля,
                          схема сьюта и выражения (L2) — чистые функции без I/O
  glafira-load-contracts  разбор OpenAPI/Swagger, proto, AsyncAPI, Avro/JSON Schema,
                          SQL-миграций, аннотаций Spring — «байты → операции»
  glafira-load-xlsx       экспорт и импорт Excel-шаблона ПРОМ
  glafira-load-engine     генераторы HTTP/Kafka/gRPC/SQL, фазы, метрики, HTML-отчёт (L2)
  glafira-load-cli        бинарник раннера и моков (L2, L4)
  glafira-load-mcp        MCP-шлюз (L5)
```

Приложение и раннер делят `glafira-load-model`: формат сьюта и профиля один, расхождений между «что показано
в приложении» и «что выполнил раннер» быть не может. Раннер не зависит от Tauri и не тянет GUI-зависимости.

## 4. Проект НТ

Папка в git. Всё текст, кроме копий заполненных Excel-шаблонов.

```
<проект>/
  glafira-load.yaml           манифест: формат, имя, сервисы СУТ, стенды
  registry/operations.yaml    реестр операций; registry/scans/ — снимки разборов
  load/prod-load.yaml         нагрузка ПРОМ после импорта; load/imports/ — оригиналы xlsx; load/profile.yaml — профиль
  suites/<имя>/suite.yaml     сьют: сценарии, шаги, проверки, ссылки на данные (L2)
  data/                       CSV/JSON Lines для подстановок (L2)
  mocks/                      описания моков и записи (L4)
  runs/                       результаты прогонов, в .gitignore; в git — только сводки по желанию (L3)
```

Сервис СУТ описывается путём к локальному клону git и списком контрактов (явные пути или автопоиск). Версия
сервиса — `git describe --tags --always --dirty` клона. Стенд — именованное окружение (`dev`, `test`, `stage`,
`prod`) с базовыми адресами: HTTP, bootstrap Kafka, gRPC, БД без пароля. Секреты стендов (SASL, пароли БД,
токены) — в OS-хранилище секретов и в переменных окружения раннера, никогда в файлах проекта (L2).

## 5. Реестр операций

Операция — единица нагрузки с устойчивым `id`: `http:<сервис>:<METHOD> <путь>`, `kafka_produce:<топик>`,
`kafka_consume:<топик>`, `grpc:<сервис>:<Service/Method>`, `sql:<сервис>:<имя>`. У операции есть сжатая схема
запроса и ответа, ссылка на файл и строку контракта, источник, отпечаток схемы, статус, версии сервиса, где
операция появилась и где видна последний раз, и ручные поля (`tags`, `notes`, `owner`), которые переживают
переразбор. Повторный разбор делает слияние: добавляет новые операции, помечает пропавшие `removed`, фиксирует
изменение отпечатка как «изменена» и пишет снимок в `registry/scans/`. Подробно — в спеке L1.

---

## 6. Нагрузка ПРОМ и профиль

Шаблон — `.xlsx` с листами «Операции», «Параметры», «Справка». ID и описание операций защищены от правки;
заполняются средний и пиковый RPS, доля ошибок, размеры запроса и ответа, p95 на ПРОМ. Импорт сопоставляет
строки по ID, показывает незаполненные, неизвестные и некорректные строки и дифф с прошлым импортом, и пишет
`load/prod-load.yaml` только после подтверждения.

Профиль нагрузки считается из цифр ПРОМ и коэффициентов: `k_env` (мощность стенда относительно ПРОМ) и
`k_growth` (запас роста), с переопределением по сервису и операции. Целевой RPS операции = RPS ПРОМ × `k_env` ×
`k_growth`; доля в смеси — отношение к сумме. Фазы: разгон, полка, ступени, спад. Несколько именованных профилей
(`nominal`, `peak`, `stress`) в одном файле. Раннер исполняет профиль как есть (L2).

---

## 7. Сьют и раннер (L2)

Сьют — YAML: сценарии из шагов (HTTP-запрос, сообщение в топик, ожидание сообщения из топика, gRPC-вызов,
SQL-запрос), проверки (код ответа, JSONPath, схема), извлечение значений из ответов для следующих шагов,
подстановки из данных и генераторов. Каждый сценарий привязан к операциям реестра, поэтому профиль нагрузки
раскладывается по сценариям, а дифф реестра (L6) указывает на затронутые сценарии.

Раннер `glafira-load run <проект> --profile peak --env test --out runs/<дата>` исполняет профиль на одном хосте
(несколько хостов — одинаковые команды с `--share 1/3`, результаты складываются в приложении), пишет метрики
по операциям и сценариям с секундным разрешением (RPS, задержки с перцентилями, ошибки по кодам, лаг потребителя
для Kafka), сырые ошибки с примерами и автономный HTML-отчёт. Команда `smoke` выполняет каждый сценарий один раз
и выдаёт список сломанных шагов. Команда `check` валидирует сьют по схеме без сети, для pre-commit и CI.

---

## 8. Моки (L4)

`glafira-load mock <проект> --mock payments` поднимает описанные в `mocks/` сервисы: HTTP и gRPC по контрактам
из реестра с задержкой и долей ошибок, потребителей и ответчиков Kafka (вычитать топик, ответить в другой),
состояние (созданный объект возвращается по id), запись через прокси перед настоящим сервисом и воспроизведение
без него. Примеры запросов и ответов берутся из логов стенда и из контрактов.

---

## 9. Отчёты (L3)

Приложение импортирует папки `runs/`, хранит историю прогонов проекта, показывает графики на uPlot (RPS,
перцентили, ошибки, лаг по времени и по операциям), сравнивает два прогона и две версии СУТ, проверяет пороги
SLA из профиля и ставит вердикт. Экспорт: CSV, текстовый формат Prometheus, PDF/DOCX по шаблону компании.

---

## 10. MCP-шлюз (L5)

Как в Glafira for Kafka: клиент (`Claude Desktop`, `Claude Code`, `Cursor`) запускает `glafira-load-testing mcp`,
шлюз соединяется с приложением по локальному сокету, каждый клиент подтверждается в диалоге, все вызовы в
аудите. Ассистент читает реестр, цифры ПРОМ, профиль, сьюты, результаты прогонов и логи стенда из указанной
папки (с маскированием как в Kafka), предлагает сценарии, данные и правки существующих сценариев. Предложение
открывается в приложении диффом, человек принимает или отклоняет. Запуск нагрузки через MCP невозможен по
построению: у бэкенда шлюза нет такой операции.

---

## 11. Сопровождение (L6)

Новая версия СУТ → повторный разбор → дифф реестра (новые, удалённые, изменённые операции) → пометка затронутых
сценариев → смоук-прогон → список на починку → предложения правок через MCP → принятие диффом → коммит.
Приложение показывает «здоровье сьюта»: доля операций из профиля, покрытых сценариями, и число сломанных шагов.

## 14. Ошибки

`AppError { code, message, details, retryable }` как в Glafira. Коды семейства плюс:

| code | Причина | Поведение UI |
|---|---|---|
| `PROJECT_INVALID` | Манифест или файл проекта не читается | Путь, строка, причина; проект открывается в режиме «только чтение» |
| `CONTRACT_PARSE` | Контракт не разобран | Файл, строка, причина; остальные контракты разбираются |
| `GIT_UNAVAILABLE` | Нет `git` или папка не репозиторий | Версия `unversioned`, предупреждение на сервисе |
| `TEMPLATE_MISMATCH` | Шаблон другого проекта или формата | Идентификаторы ожидаемый/найденный |
| `TEMPLATE_INVALID` | Строки с ошибками | Список строк, импорт заблокирован до исправления |
| `PATH_OUTSIDE_PROJECT` | Запись или чтение за пределами проекта или клона | Отказ |
| `RUN_INCOMPLETE` (L3) | Папка прогона без итоговой сводки | Импорт частичных данных с пометкой |

## 15. Тестирование и нефункциональные требования

- Крейты без I/O покрыты unit-тестами на фикстурах (`dev/fixtures/`); round-trip Excel; идемпотентность слияния
  реестра; свойства расчёта профиля (сумма долей = 1, монотонность по коэффициентам).
- Фронтенд: vitest + Testing Library; `i18n-check` с обязательными `en` и `ru`.
- Раннер (L2): интеграционные тесты против локального стенда в `dev/docker-compose.yml` (echo-HTTP, Kafka,
  gRPC-заглушка, PostgreSQL), пропускаются без переменных `GL_IT_*`.
- CI: `cargo test`, `cargo deny`, `pnpm test`, `i18n:check`, сборка установщиков на macOS, Windows, Linux и
  статического раннера под `x86_64-unknown-linux-musl` и `aarch64-unknown-linux-musl`.
- Доступность: вся работа с клавиатуры, фокус-ловушки в диалогах, подсказки «?» как в семействе.
- Производительность: реестр на 5 000 операций открывается без задержки (виртуализация таблиц), разбор 200
  контрактов — в фоне с прогрессом и отменой.
